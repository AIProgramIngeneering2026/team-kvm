# ADR-0001. Модульный монолит вместо микросервисов

- **Дата:** 2026-11-15
- **Статус:** предложено (становится «принято» после одобрения PR командой)
- **Связанные документы:** [architecture.md](../architecture.md), [tool-contract.md](../tool-contract.md), [ADR-0002](0002-async-jobs.md)

## Контекст и ограничения

Сервис принимает один PDF или TXT, создаёт Job, извлекает текст или считает статистику и сохраняет результат (см. [requirements.md](../requirements.md)). Нужно выбрать, как разложить систему по процессам.

Что известно о проекте:

- Это учебный MVP: небольшая команда, срок — один семестр, затем добавляются LLM-инструменты.
- Домен один и небольшой: Job, два Tool, чтение документов, хранение.
- В плане запуск через Docker Compose, CI, логирование и health check. Отдельная инфраструктура для каждого сервиса на это не рассчитана.
- Нагрузка невелика: максимальный размер файла — 10 МиБ, одна Job обрабатывает один документ.
- Компоненты (HTTP API, JobService, JobRunner, Dispatcher, Registry, Tool, DocumentReader) уже описаны в архитектуре и общаются обычными вызовами внутри одного приложения.

## Решение

Строим **модульный монолит**: одно приложение, которое разворачивается как один процесс (плюс база данных и хранилище файлов). Внутри приложения — модули с явными границами:

| Модуль | Граница |
|---|---|
| HTTP API | Единственная точка входа для клиента; не знает про Tool и хранилище. |
| JobService + JobRepository | Правила Job, состояния, идемпотентность; SQL скрыт за репозиторием. |
| JobRunner | Фоновое исполнение; см. [ADR-0002](0002-async-jobs.md). |
| Dispatcher + Registry + Tool | Общий интерфейс `Tool.execute(ToolInput) -> ToolResult`; Tool не знает про HTTP и состояния Job. |
| DocumentReader | Единственное место, где читаются PDF и TXT. |
| ExternalHttpAdapter (план) | Единственное место, где вызывается внешний HTTP-сервис. |

Правила, которые сохраняют модульность:

1. Модули общаются через интерфейсы (`Tool`, `DocumentReader`, репозиторий), а не через внутренности друг друга.
2. Зависимости кода идут в одну сторону: API → JobService → репозиторий и JobRunner → Dispatcher → Tool → DocumentReader. Tool не импортирует JobService и HTTP-слой.
3. Новый инструмент (в том числе LLM во втором семестре) добавляется как ещё один Tool через Registry без изменения Dispatcher и JobService.

## Рассмотренные альтернативы

**1. Микросервисы** (отдельные сервисы API, исполнителя и инструментов, общение по HTTP или через брокер).
Плюсы: независимое масштабирование и деплой, изоляция падений.
Почему отвергнуто: для двух простых Tool и небольшой команды накладные расходы несоразмерны — сетевые контракты между сервисами, сетевые отказы внутри системы, распределённая отладка, несколько образов в Compose и CI. Эти расходы нужно оплатить до первой работающей операции, а выигрыш при такой нагрузке не проявится.

**2. Монолит без внутренних границ** («всё в одном модуле»).
Плюс: быстрее всего начать.
Почему отвергнуто: LLM-инструменты придётся добавлять в уже запутанный код, а Tool-контракт и разделение ответственностей из архитектуры потеряют смысл.

**3. Монолит с отдельным процессом-исполнителем** (API и worker из одной кодовой базы, но два процесса).
Это не про границы модулей, а про способ запуска Job, поэтому решение вынесено в [ADR-0002](0002-async-jobs.md).

## Цена решения

- Единое масштабирование: нагрузить можно только весь процесс целиком, а не отдельный Tool.
- Один язык и одно окружение для всех модулей.
- Нет изоляции падений: ошибка нативной библиотеки при разборе PDF (например, в PyMuPDF) может остановить весь процесс, включая API. Последствия для Job описаны в [ADR-0002](0002-async-jobs.md) (`WORKER_INTERRUPTED`).
- Границы модулей держатся на дисциплине команды и code review: компилятор их не проверяет. Нарушение (например, импорт репозитория напрямую из Tool) нужно ловить на ревью.
- Деплой выполняется целиком: любое изменение требует пересборки и перезапуска всего приложения.

## Условия пересмотра

Решение стоит пересмотреть, если выполняется хотя бы одно условие:

- LLM-инструменты второго семестра требуют отдельных ресурсов (GPU, большая память, долгие вызовы) или другого стека, и это мешает остальному сервису;
- один Tool нужно масштабировать независимо от остальных;
- падения парсера PDF начали регулярно останавливать API, и изоляции отдельным процессом уже недостаточно;
- Tool или DocumentReader нужно использовать из другого проекта как самостоятельный сервис;
- над разными частями системы работают команды, которым мешает общий цикл выпуска.

Первым шагом при пересмотре будет вынос JobRunner в отдельный процесс (см. [ADR-0002](0002-async-jobs.md)), а не переход сразу к микросервисам.
