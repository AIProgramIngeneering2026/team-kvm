## Требования к системе

## 1. Назначение системы

Сервис автоматической обработки текстовых документов.

Система предназначена для пользователей, которым необходимо извлекать текст из документов, получать статистику их содержимого и сохранять результаты обработки.

Основные пользователи - студенты, преподаватели и другие люди, работающие с текстовыми материалами.

### Возможности первой версии

- Приём документов в форматах PDF и TXT.
- Извлечение текста из поддерживаемых документов.
- Подсчёт количества слов и символов.
- Определение количества страниц PDF.
- Отслеживание состояния обработки.
- Получение результатов по идентификатору задачи.
- Сохранение истории выполнения задач.
- Обработка некорректных файлов и ошибок выполнения.

### Ограничения

- PDF должен содержать текстовый слой.
- TXT должен иметь поддерживаемую текстовую кодировку (для MVP — UTF-8).
- Максимальный размер файла предлагается ограничить 10 МБ.
- Распознавание сканированных документов не входит в базовый MVP.
- Обработка нескольких документов в рамках одной Job не поддерживается.
- Интеграция с LLM планируется на следующий семестр.
- Работа с конфиденциальными документами не предусмотрена в учебном MVP.

## 2. Пользовательские сценарии

### UC-01. Извлечение текста из TXT

**Участник:** пользователь сервиса.

**Цель:** получить текстовое содержимое TXT-файла.

**Основной поток:**

1. Пользователь выбирает файл формата TXT.
2. Пользователь отправляет файл и указывает операцию `extract_text`.
3. Система проверяет файл и создаёт Job со статусом `created`.
4. Система переводит Job в `running` и выполняет извлечение текста.
5. Результат сохраняется, Job переходит в `done`.

**Критерии приёмки:**

- **Дано:** пользователь подготовил корректный TXT-файл в кодировке UTF-8.
- **Когда:** пользователь отправляет запрос на извлечение текста.
- **Тогда:** система создаёт Job и возвращает её уникальный идентификатор.
- **И:** после успешного выполнения Job имеет статус `done`, а результат содержит текст файла.

### UC-02. Извлечение текста из PDF

**Участник:** пользователь сервиса.

**Цель:** получить текст из PDF-документа.

**Основной поток:**

1. Пользователь выбирает PDF-документ с текстовым слоем.
2. Пользователь отправляет документ с операцией `extract_text`.
3. Система создаёт Job.
4. Инструмент извлекает текст из страниц PDF.
5. Система сохраняет текст и количество страниц, завершает Job со статусом `done`.

**Критерии приёмки:**

- **Дано:** PDF-документ содержит доступный для извлечения текст.
- **Когда:** выполняется операция `extract_text`.
- **Тогда:** Job завершается со статусом `done`.
- **И:** результат содержит извлечённый текст и количество страниц документа.

### UC-03. Получение статистики документа

**Участник:** пользователь сервиса.

**Цель:** узнать основные характеристики текстового содержимого документа.

**Основной поток:**

1. Пользователь выбирает документ PDF или TXT.
2. Пользователь отправляет документ с операцией `text_statistics`.
3. Система создаёт Job.
4. Инструмент получает текст документа и подсчитывает слова и символы.
5. Система сохраняет статистику и переводит Job в `done`.

**Критерии приёмки:**

- **Дано:** пользователь отправил корректный поддерживаемый документ с известным содержимым.
- **Когда:** система выполняет операцию `text_statistics`.
- **Тогда:** результат содержит количество слов и символов, соответствующее согласованным правилам подсчёта.
- **И:** для PDF указывается количество страниц.

Количество символов учитывает пробелы и переносы строк. Правило определения слов фиксируется при проектировании контракта операции.

### UC-04. Получение состояния и результата Job

**Участник:** пользователь сервиса.

**Цель:** узнать, завершилась ли обработка документа, и получить результат.

**Основной поток:**

1. Пользователь отправляет документ на обработку.
2. Система возвращает идентификатор Job.
3. Пользователь запрашивает состояние Job по идентификатору.
4. Система находит Job в хранилище.
5. Система возвращает текущее состояние и доступный результат обработки.

**Критерии приёмки:**

- **Дано:** в системе существует Job с известным идентификатором.
- **Когда:** пользователь запрашивает информацию об этой Job.
- **Тогда:** система возвращает её актуальное состояние.
- **И:** если Job имеет статус `done`, пользователь получает сохранённый результат.
- **И:** если Job ещё выполняется, система сообщает статус `created` или `running`, не выдавая незавершённый результат как готовый.

### UC-05. Отправка неподдерживаемого формата (ошибочный сценарий)

**Участник:** пользователь сервиса.

**Цель:** получить понятное сообщение о невозможности обработки неподдерживаемого файла.

**Основной поток:**

1. Пользователь выбирает файл неподдерживаемого формата, например EXE.
2. Пользователь отправляет его на обработку.
3. Система проверяет формат файла.
4. Система обнаруживает неподдерживаемый формат.
5. Запрос отклоняется с понятным сообщением об ошибке.

**Критерии приёмки:**

- **Дано:** пользователь выбрал файл неподдерживаемого формата.
- **Когда:** файл отправляется на обработку.
- **Тогда:** система отклоняет запрос с кодом ошибки `UNSUPPORTED_FORMAT`.
- **И:** Job не создаётся.
- **И:** сообщение об ошибке указывает поддерживаемые форматы.

### UC-06. Обработка повреждённого PDF (ошибочный сценарий)

**Участник:** пользователь сервиса.

**Цель:** получить информацию о неудачной обработке повреждённого документа.

**Основной поток:**

1. Пользователь отправляет файл с допустимым форматом PDF.
2. Система принимает запрос и создаёт Job.
3. Job переходит в `running`.
4. Инструмент обнаруживает, что содержимое PDF повреждено и не может быть прочитано.
5. Система фиксирует ошибку и переводит Job в `failed`.

**Критерии приёмки:**

- **Дано:** файл имеет допустимый формат загрузки, но повреждён внутри.
- **Когда:** инструмент пытается прочитать PDF.
- **Тогда:** Job переходит в состояние `failed`.
- **И:** результат содержит код ошибки `DOCUMENT_CORRUPTED` и описание проблемы.
- **И:** повреждённый документ не приводит к остановке всего сервиса.

## 3. Жизненный цикл Job

Job — единица работы по обработке одного документа с выбранной операцией.

### Состояния

| Состояние | Описание |
|---|---|
| `created` | Задача создана и ожидает выполнения |
| `running` | Задача находится в процессе выполнения |
| `done` | Обработка успешно завершена |
| `failed` | Обработка завершилась ошибкой |

### Разрешённые переходы

- `created → running` — начало выполнения.
- `running → done` — успешное завершение.
- `running → failed` — ошибка при выполнении.

### Запрещённые переходы

- `created → done` — нельзя завершить задачу без перехода к выполнению.
- `done → running` — завершённая задача не запускается повторно.
- `failed → done` — ошибочная задача не становится успешной без новой обработки.
- `failed → running` — повторное выполнение ошибочной Job в базовом MVP не предусмотрено.

Попытка недопустимого перехода должна отклоняться с понятной ошибкой и не должна изменять сохранённое состояние Job.

### Дополнительные правила

- Каждая Job имеет уникальный идентификатор.
- Job содержит выбранную операцию и её параметры.
- Успешная Job содержит результат выполнения.
- Ошибочная Job содержит сведения о причине неудачи.
- История состояний должна сохраняться.

## 4. Что предложил ИИ

Для выявления дополнительных проблем основного сценария обработки PDF была использована языковая модель ChatGPT.

### Промпт

Мы разрабатываем сервис обработки PDF и TXT. Пользователь отправляет PDF с текстовым слоем, система создаёт Job, извлекает текст и сохраняет результат. Предложи три ситуации, которые могут нарушить нормальную работу этого сценария. Не повторяй случаи неподдерживаемого формата и повреждённого PDF. Для каждого случая объясни последствия и предложи ожидаемое поведение системы.

### Предложение 1. Повторная отправка одного запроса

**Проблема:** пользователь дважды отправляет один и тот же запрос из-за повторного нажатия кнопки или сетевого сбоя.

**Последствия:** система может создать две Job и дважды выполнить одинаковую операцию.

**Решение: принимаем.**

Для запросов с одинаковым ключом идемпотентности и одинаковыми параметрами система должна возвращать существующую Job, а не создавать новую. Это поведение будет детализировано при проектировании API.

### Предложение 2. PDF не содержит извлекаемого текста

**Проблема:** пользователь отправляет корректный PDF, страницы которого являются сканированными изображениями.

**Последствия:** извлечение обычного текста возвращает пустой результат, хотя документ визуально содержит информацию.

**Решение: принимаем.**

Для операции `extract_text` система должна обнаруживать отсутствие извлекаемого текста и завершать Job со статусом `failed`, возвращая ошибку `TEXT_NOT_FOUND`.

Поддержка OCR остаётся за пределами базовой версии. Возможность подключения внешнего OCR-сервиса будет рассмотрена отдельно.

### Предложение 3. Пользователь запрашивает результат до завершения обработки

**Проблема:** пользователь отправляет большой документ и сразу запрашивает результат, пока задача выполняется.

**Последствия:** система может ошибочно вернуть пустой результат как окончательный.

**Решение: принимаем.**

Система должна возвращать текущее состояние Job. Пока выполнение не завершено, готовый результат недоступен. После перехода в `done` результат становится доступным для получения.

Это поведение отражено в сценарии UC-04.

## 5. Планируемое расширение системы

### В течение текущего семестра

Реализуется backend-сервис обработки документов с архитектурой Job → Dispatcher → Registry → Tool → ToolResult.

Планируется:

- HTTP API и машиночитаемый контракт.
- Два инструмента: `ExtractTextTool` и `TextStatisticsTool`.
- Хранение истории задач и результатов с миграциями БД.
- Внешняя HTTP-интеграция через адаптер с timeout, retry и fake-реализацией для тестов.
- Автоматизированные тесты и CI.
- Логирование, health check и запуск через Docker Compose.

### Во втором семестре

Планируется добавление LLM-инструментов для:

- Создания кратких конспектов документов.
- Выделения основных мыслей и понятий.
- Классификации документов.
- Генерации вопросов по содержимому.
- Ответов на вопросы пользователя с опорой на содержимое документов.

LLM будет подключаться как новый инструмент через существующий контракт без необходимости переписывать управляющую логику системы.
